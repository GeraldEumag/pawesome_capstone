# Phase 3 Inventory Master Audit

**Audit stage:** Phase A-E audit, bounded remediation, and isolated verification  
**Baseline:** `audit/pawesome-final-acceptance` at `afd48899e3aa92e65aa0d2364229d5010ad6d9a6`  
**Phase 3 implementation:** Four confirmed findings addressed; no application migration added  
**Scope:** Inventory lifecycle, including product identity, stock movements, batches, returns, authorization, POS/service integrations, reports, and frontend/API contracts.

## Executive verdict

The repository already contains a substantial inventory-management system, not a CRUD-only module. A previous isolated full-stack inventory audit recorded fixes for stock adjustment endpoints, stock-out authorization, movement attribution, batch disposal, low-stock notification persistence, and date/time handling. Existing source shows transactional stock mutation, item and batch locks, FIFO/FEFO issue logic, stock-request approvals, return inspection/disposition, and inventory usage links to POS and service workflows.

Phase 3 source inspection found a high-impact gap in source-linked return quantity enforcement: the limit is read and a return is inserted without a transaction or item/source lock. Concurrent requests can both observe the same remaining return quantity and exceed it. The UI does send idempotency keys, but it creates a new key for each submit attempt, so an uncertain retry is not replayed. Two product-form/API contract mismatches were also confirmed: the form requires an SKU even though the backend has an established SKU generator, and it tells users a barcode may be left blank although new items default to sellable and the backend requires a barcode for sellable items.

The initial, bounded implementation plan was recorded before any source edit in `09-test-results-and-implementation-changelog.md`. Four confirmed findings were addressed. Phase 3 is **PARTIALLY ACCEPTED / NOT COMPLETE**: isolated tests and the production build pass, but browser E2E was not run and unit conversion, barcode-generation standard, brand-catalog, warranty, production parity, and MySQL 8 questions remain unresolved.

## Architecture discovered

| Layer | Actual implementation |
| --- | --- |
| Catalog | `inventory_items` is the product/inventory record; fields include name, generic name, brand, category, SKU, barcode, status, unit, price, cost, stock, reorder level, supplier link, expiry tracking, and sellability. No separate product or brand-catalog table was evidenced in the inspected inventory migrations. |
| Receiving/lots | `inventory_batches` holds received/remaining integer quantities, lot number, received/manufactured/expiry dates, supplier, unit cost, and status. Stock-in transactions group movement rows by `transaction_no`; no dedicated purchase-order/receiving-header model was found in the inspected inventory code. |
| Ledger/audit | `inventory_logs` records movement type, quantity/delta, before/after balances, reason, actor, reference and transaction metadata. `inventory_monthly_audits` records physical-count variance and manager approval. |
| Requests/returns | `inventory_stock_requests` and `_items` implement approval for sensitive stock-out reasons. `inventory_returns` implements a customer-product return inspection/disposition lifecycle. |
| Shared backend | `App\Services\InventoryService` owns item creation/update/archive, adjustments, stock deduction/receiving, reconciliation, movement reversals, and return handling. Inventory and admin controllers delegate stock changes to this service per the current code and prior audit. |
| Integrations | POS uses `InventoryService::deductStock`; veterinary, grooming, boarding, and boarding add-on services record usage and use the shared mutation service. Phase 2 makes POS prices, descriptions, transactions, and stock deductions server-authoritative and idempotent. |
| Frontend | `InventoryRoutes.jsx` routes to catalog, stock-in/out, returns, movement, batch, audit, reports, supplier, and barcode-label pages. `inventory.jsx` is the API facade. `AddProductModal`, `BarcodeGenerator`, `StockInPage`, `StockOutPage`, and `StockReturnsPage` are the key inspected workflows. |
| Authorization | Admin inventory routes use the `admin` role; inventory routes use `admin,inventory`; sensitive stock-request approvals use manager/admin routes. Barcode lookup is authenticated and role-restricted to cashier/inventory/admin. Existing authorization tests cover denied direct API writes. |

## Findings matrix

| ID | Classification / severity | Finding and source evidence | Impact / recommendation | Test required |
| --- | --- | --- | --- | --- |
| INV3-01 | Confirmed technical defect / P1 | `InventoryService::createReturn()` reads the item, calls `validateReturnSource()` (which sums prior returns), then inserts `InventoryReturn` without a transaction or lock. The source limit is not represented by a unique database constraint. Evidence: `backend/app/Services/InventoryService.php` (`createReturn`, `validateReturnSource`); `backend/database/migrations/2026_11_22_000001_stock_movement_system.php` (return table has unique `return_no`, not a source/item aggregate constraint). | Concurrent source-linked submissions can exceed sold quantity, allowing excess returned stock to be later restocked. Put validation and creation in one transaction and serialize source-limit checks by locking the inventory item before counting/creating. Preserve the existing policy that all dispositions count against the physically returned quantity. | Feature test with two concurrent requests returning the final unit; exactly one succeeds and only one return row is created. |
| INV3-02 | Confirmed technical defect / P2 | `StockReturnsPage.submitCreate()` calls `newIdemKey()` inline for every attempt. `IdempotencyKey` only replays when the same user/key/route/payload is retried. Evidence: `frontend/src/components/inventory/StockReturnsPage.jsx`; `backend/app/Http/Middleware/IdempotencyKey.php`; route middleware at `backend/routes/api.php` (`POST inventory/returns`). | An uncertain network outcome followed by retry uses a different key and can create another return. Keep one key for the in-flight logical submission and reuse after uncertain failures; rotate after success or a definitive validation response. | Feature test same-key replay yields one return; frontend test verifies the key is reused across retry and reset after success. |
| INV3-03 | Confirmed frontend/backend mismatch / P2 | `AddProductModal.validateStep()` rejects an empty SKU, while `InventoryService::createItem()` and `generateSKU()` generate one when blank. The model also has a legacy creation fallback. Evidence: `frontend/src/components/inventory/AddProductModal.jsx`; `backend/app/Services/InventoryService.php` (`createItem`, `generateSKU`). | The UI blocks the existing server-generated SKU path and forces manual entry. Make SKU optional in the UI and let the existing server generator remain authoritative; do not change its format. | Frontend test submits blank SKU and accepts the server response containing the generated value; retain backend duplicate-SKU regression tests. |
| INV3-04 | Confirmed frontend/backend mismatch / P2 | `AddProductModal` labels barcode optional and says “Leave blank if none”; it exposes no `is_sellable` control. `InventoryService::validateItemData()` treats omitted sellability as true and requires barcode on create for sellable items. Evidence: `frontend/src/components/inventory/AddProductModal.jsx`; `backend/app/Services/InventoryService.php` (`validateItemData`). | Product creation can reach a server 422 after the UI has represented the field as optional. Align the label and client validation with the existing sellable-item rule; do not auto-generate or invent a barcode value. | Frontend test shows a clear barcode validation message before request; backend tests preserve required-for-sellable and uniqueness behavior. |
| INV3-05 | Incomplete requirement / POLICY BLOCKED | `inventory_items.unit` and `service_item_usages.unit` store labels, while item stock, batches, movements, and service usage quantities are integer-valued. No conversion ratio/base-unit model was found. Evidence: `2026_11_22_000001_stock_movement_system.php`, `2026_05_11_140000_create_service_item_usages_table.php`, `InventoryItem`, and `ServiceItemUsage`. | Piece/pack/box conversion cannot safely be inferred. Obtain approved base units and item-specific conversion/rounding rules before implementing. | No conversion test is appropriate until policy is approved. |
| INV3-06 | Incomplete requirement / POLICY BLOCKED | Product barcode entry/scanning, lookup, CODE128 label rendering/printing, and a “Save SKU as Barcode” action exist. No backend-generated unique barcode is assigned on product creation. Evidence: `AddProductModal.jsx`, `BarcodeGenerator.jsx`, `InventoryService::validateItemData()`, and the unique barcode index migration. | Distinguish scanning, lookup, label rendering, and identifier assignment. The earlier compliance audit marks automatic barcode generation missing and requests panel/client confirmation; barcode format and whether SKU is an acceptable identifier are not approved here. Do not silently create a new format. | Barcode uniqueness/lookup tests exist; generation-specific tests are NOT RUN / not applicable until policy approval. |

Earlier checklist X-03 asks for SKU/brand dropdown/autogeneration. | Confirm whether a reusable brand catalog is required and who may add values; no new table or inferred brand source is proposed in this phase. | Existing field persistence tests only; dropdown behavior is NOT RUN. |
