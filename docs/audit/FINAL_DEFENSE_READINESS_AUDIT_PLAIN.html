Final Defense-Readiness Audit Report

Pawesome Pet Care Management System · Audit date: November 17, 2026 · Branch: main @ a7f93ca

What this report is

This is the final check of the whole Pawesome system before the capstone defense. The goal was simple: will the system hold up when panelists try to break it? We tested it the way a panel might — entering wrong information, clicking things twice, refreshing mid-transaction, switching between roles, generating reports right after making a sale, and trying to access things they should not be allowed to see.

Nothing in the system was changed during this audit. Everything below is a report of what we found, plus a plan for what to fix — waiting for approval before any work starts.

1. The short answer

The system is in good shape for the defense — with one real bug that should be fixed first.

  • Every major feature was tested live and worked: ordering, booking, approvals, payments, receipts, inventory deduction, veterinary records, and reports.
  • All the "break it" attempts were handled correctly: double-clicks, duplicate submissions, expired sessions, wrong file uploads, other people's data, oversized numbers, and two cashiers selling the last item at the same time.
  • One bug found: the Sales Report shows an empty report whenever a date filter is used, even though sales exist. A panelist who makes a sale and then opens a filtered sales report will see "No records found." This is the classic demo trap and should be fixed before the defense.

2. How we tested it

To keep the real data safe, all testing was done on a separate copy of the database. The normal development database was only read, never written to. Emails were switched to a safe "pretend" mode so no real messages were sent to anyone.

We tested in three ways:

  • Reading the code — checking how each feature is built, how permissions are applied, and how money and stock are handled.
  • Running the automated test suites — 986 backend checks and 33 frontend checks that the team already had, plus four larger audit tools.
  • A live hands-on probe — a script that acts like a real user: registering, booking, paying, uploading proofs, running the cash register, doing a vet consultation, pulling reports, and deliberately trying to break things. 98 separate checks, verified against the database afterward.

4. The one real problem we found

Problem: The Sales Report always shows "No records found" whenever a date range is selected — even though sales exist.

Seen live: calling the Sales Report with no filter shows all 35 sales (₱5,785). Adding any date filter — even a wide one covering the whole month — returns zero rows.

Why it happens (in plain terms): the report's date filter looks at a column called created_at, but two tables in the same query have a column with that name, so the database can't tell which one is meant and throws an error. Worse, the code is designed to quietly hide errors and show "no data" instead — so the failure looks like an empty report rather than a broken one.

Why it matters: a panelist's natural move is "make a sale, open the sales report for today." Right now they would see an empty report — which looks like a bigger problem than it is.

Fix: a one-line change to name the correct table's column, plus making report errors visible instead of hidden. No data is damaged — this is a display/query issue only. Proposed as the first item in the fix plan below.

5. Problems with our test tools (not the app)

Three of the older audit tools had outdated assumptions — these are issues with the testing scripts, not with Pawesome itself:

  • Gate A (cross-role test): its random booking times mostly land on "half-past" minutes that the system correctly rejects, plus it sometimes picks 9 AM (before the 10 AM opening). After 46 fixture-caused retries, a clean run passed 31/31 checks — confirming the full customer→receptionist→cashier→vet→manager chain works.
  • Gates C & D (database/report checks): they look for a table called vet_appointments that was deliberately removed in a past cleanup. Every check that ran before that point passed (99 checks on Gate C; all reconciliation on Gate D matched exactly).
  • Gate B (security): 6 of its "failures" expected the admin account to be blocked from staff pages — but admin is designed to reach all staff modules. We verified admin is still correctly blocked from customer pages, so this is a stale expectation in the script.

These tools should be updated so future audits give cleaner signal.

6. What we could not test

  • Real email sending (Brevo) — needs live credentials; tested in safe pretend mode only.
  • Telegram and live-chat delivery — external services, no credentials available.
  • MySQL 8 behavior — the local machine runs MariaDB 10.4; the project's own CI is the authoritative MySQL 8 check.
  • Full browser walkthrough — the live probe exercised the API and database directly; a full Playwright UI pass was not part of this run.
  • Production settings — debug mode is on and the database password is empty locally, as expected for development. These are already on the release checklist for deployment.

Bottom line for the defense

Pawesome is functionally solid, secure, and hard to break — every "panelist attack" we tried was handled correctly, and every module talks to the others properly. The single real bug is the Sales Report's date filter, which a panelist is quite likely to trigger. Recommendation: approve the small fix (Step A), re-verify, and the system is defense-ready.
